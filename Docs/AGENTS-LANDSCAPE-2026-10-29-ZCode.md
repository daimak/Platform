# Агенты: ландшафт и как подступиться — справка ZCode

> Составлено: ZCode, 2026-10-29, по запросу Sovereign. Снимок ландшафта на
> октябрь 2026 + разбор «как это работает у знакомых» + дорожная карта для
> Platform Evo. Формат наследует `Docs/AI-ONBOARDING.md`. Источники — с датами,
> в разделе 8; мои собственные наблюдения помечены **[опыт]**.

## TL;DR

1. «У меня 2 десятка агентов, всё чётко» почти всегда означает: **один
   оркестратор + папка ролевых промптов + набор инструментов**. Не 24
   автономных робота, а 24 текстовых файла с ролями, которые один движок
   подставляет по мере надобности.
2. Ценность создаётся не количеством агентов, а тремя вещами: **контрактами
   инструментов, качеством контекста и проверкой результата**. Агентов без
   инструментов не существует — есть болтуны.
3. Platform Evo уже стоит на правильной половине архитектуры: ADR-004/005 —
   это контракты инструментов, `Memory/Agents/*.md` — готовые ролевые
   промпты, канонический формат вывода — готовый контракт проверки. Не
   хватает рантайма: кто подставляет паспорт в системный промпт, кто вызывает
   инструменты, кто меряет результат. Это ~50–100 строк Python, не фреймворк.

## 1. Базовый словарь (пять минут)

- **Агент** = LLM + цикл «план → действие → наблюдение» + **инструменты** +
  контекст. Всё остальное (имя, характер, паспорт) — оформление.
- **Инструмент (tool)** — функция с описанным контрактом: «парсить страницу»,
  «прочитать git log», «записать файл в разрешённую папку». У вас это
  закреплено в ADR-005.
- **MCP (Model Context Protocol)** — открытый стандарт, позволяющий
  подключать инструменты к агенту как «USB-устройства»: один протокол — много
  готовых серверов (файлы, git, браузер, БД). Сейчас это самый быстрый способ
  дать агенту «руки».
- **Субагент** — агент, которого вызывает другой агент с чистым контекстом:
  основной агент не пачкает своё окно деталями, субагент возвращает только
  вывод. **[опыт]** Именно так в этой сессии устроены мои субагенты-поисковики.
- **Скилл (skill)** — переиспользуемая инструкция/процедура («как проводить
  аудит»), которую агент подгружает по необходимости.
- **Хук (hook)** — принудительное правило на уровне движка («перед коммитом —
  проверить», «запрещённые команды — стоп»). Это защита не от агента, а от
  его ошибок.
- **Паспорт агента** — ваш собственный термин из `Memory/Agents/README.md`:
  мандат + входы + канонический формат вывода. По сути — системный промпт с
  контрактами. Общепризнанная практика 2026 делает ровно это, только без
  красивого названия.

Мнемоника из практики Claude Code (2026): **скиллы — знания, субагенты —
чистое рабочее пространство, MCP — руки, хуки — принуждение, плагины —
упаковка.**

## 2. Что на самом деле стоит за «у меня 2 десятка агентов»

Три типовых стека, в порядке распространённости:

**A. CLI-агент + папка ролей** (самый частый у «знакомых»). Claude Code /
ZCode / аналогичный движок, рядом — каталог субагентов и скиллов
(«парсер», «аналитик», «репортёр», «скриптёр»), плюс пара MCP-серверов.
«Двадцать агентов» = двадцать markdown/yaml-файлов по 30–60 строк. Работает
чётко, потому что задачи рутинные и каждая замыкается на 1–2 инструмента.
**[опыт]** Это ровно та механика, которой пользуешься ты прямо сейчас:
пятничная сводка — автоматизация-агент, паспорта — роли, ZCode — движок.

**B. Нодовый автоматизатор** (n8n, Make). Визуальные цепочки: триггер →
LLM-нода с ролью → HTTP/парсер → отчёт в Telegram. Для DevOps-человека
самый наглядный вход: видно поток данных, легко отлаживать, есть
self-hosted n8n под твой контур.

**C. Код-фреймворк** (LangGraph, CrewAI, AutoGen, OpenAI Agents SDK).
Нужен, когда появляются циклы с состоянием, ветвления, ретраи, «агент
проверяет агента». В 2026 LangGraph обошёл CrewAI по внедрению в
enterprise-сегменте (Pickaxe, 2026); CrewAI силён в ролевых командах
(ближе всего к вашим паспортам); AutoGen — в диалогах агентов между собой.

Важная правда про «2 десятка»: у большинства это 3–4 реально работающих
сценария, оформленных как 20 ролей. Это не плохо — это и есть нормальная
зрелость. Просто не надо мерить агентами; надо мерить задачами.

## 3. Паттерны оркестрации — когда какой применять

Канонический набор 2026 (Mastra, build5nines, Gamut — см. источники):

| Паттерн | Суть | Ваш пример |
|---|---|---|
| Цепочка (prompt chaining) | Пошагово, выход шага — вход следующего | парсинг → нормализация → отчёт |
| Параллелизация (fan-out/fan-in) | N независимых задач, сборка результата | сводки по N источникам за раз |
| Роутинг | Классификатор направляет запрос профильному агенту | «это аудит? → Холмсу» |
| Оркестратор-воркеры | Координатор раздаёт задачи специалистам | Бэрримор → Соломон/Холмс (ваш дизайн) |
| Оценщик-оптимизатор (generator-critic) | Один генерирует, другой проверяет | Холмс критикует отчёты Бэрримора |
| Чёрная доска (общая память) | Агенты пишут/читают общее состояние | у вас это уже файлы + git |

Правило из консенсуса сообщества: **мультиагентность оправдана, только если
задача чисто декомпозируется** на независимые подзадачи с ясными ролями и
передачами. Иначе один агент с хорошими инструментами проще, дешевле и
надёжнее.

## 4. Ловушки, о которых знакомые не рассказывают

1. **Пропасть демо→прод.** По Gartner (цит. по Medium, 2026) ~88% агентных
   пилотов не доезжают до продакшена. Причина не в моделях, а в обвязке:
   планирование, память, обработка ошибок, метрики.
2. **Тихие провалы хуже падений.** Агент, который молча вернул неверный
   отчёт, стоит дороже агента, который упал с ошибкой. Антидот: канонический
   формат вывода с полем «уверенность/не знаю» (у вас он уже задуман) и
   обязательная телеметрия рукопожатий.
3. **LLM нельзя делать собственным оградителем.** «Проверь сам себя» не
   работает — проверка должна быть отдельной ролью/правилом (hooks,
   evaluator-optimizer).
4. **Стоимость растёт нелинейно.** Каждое рукопожатие агентов — новый
   вызов LLM с полным контекстом. Цепочка из 6 звеньев на 20k токенов — это
   уже 120k токенов на одну задачу. Твой локальный шлюз :31415 снимает
   денежную часть вопроса — это реальное преимущество.
5. **Агентный театр.** Много агентов, ноль измеримой пользы. Антидот —
   заводить агента только под задачу с проверяемым результатом (правило
   из раздела 6).
6. **Отладка.** Падение цепочки агентов отлаживать труднее, чем код:
   нужны логи каждого вызова. **[опыт]** В этой сессии самым полезным для
   расследований оказывался не «ум» агентов, а журналы: git, LOG.md, AI-Usage.

## 5. Карта вашей ситуации (Platform Evo)

**Уже есть (доказательства путями):**

- Роли и мандаты: `Memory/Agents/` — Бэрримор (частично активен), Соломон и
  Холмс (на утверждении), в текстах упомянуты Видящий, Квотермейн, Синдбад,
  Рокфеллер, Архитектор, Доктор Стоун. Это готовый штат, только без рантайма.
- Канонический формат вывода «Вывод / Факты / Варианты / Риски /
  Рекомендация» — готовый контракт для evaluator-оптимизатора.
- ADR-004 (агенты не касаются ОС, всё через инструменты с разрешениями) и
  ADR-005 (всё — инструмент, ничего вне реестра) — это профессиональный
  уровень безопасности и гигиены, которого многим «знакомым» не хватает.
- Работающий генератор брифов `tools/barrymore/morning-brief-agent.py`
  (stdlib-only, локальный шлюз), лиджер `Memory/Engineering/Tasks/`.
- Телеметрия зачатком: AI-Usage журнал в `%LOCALAPPDATA%\Platform\AI-Usage\`.

**Чего не хватает (разрывы):**

1. **Рантайм оркестрации.** Паспорта лежат, но никто не подставляет их как
   system prompt по событию/расписанию и не собирает ответы.
2. **Реестр инструментов.** ADR-005 декларирует «всё — инструмент», но
   реестра (файл со списком: имя, контракт, права) нет. Это первый артефакт,
   который надо сделать.
3. **Проверяющий.** Холмс описан, но не запущен; нет ни одной пары
   «генератор + критик» в работе.
4. **Триггеры.** Планировщик уже есть (пятничная сводка, таски Бэрримора) —
   его можно расширять, отдельная инфраструктура не нужна.

## 6. Дорожная карта «как подступиться» (без нового фреймворка)

**Этап 0 — выбрать 2–3 реальные боли (выходные).** Не «агентов ради
агентов». Кандидаты уже лежат в репозитории:

- парсинг автосервисов — `tools/autoservices_search.py` уже написан и ждёт
  в untracked; это готовый «инструмент парсера»;
- еженедельный аудит Холмса — половина работы уже автоматизирована
  пятничной сводкой (git log/status + журнал), не хватает вердикта по
  каноническому формату;
- фильтрация `Notes/Inbox.md` Соломоном: приоритезация входящих идей.

**Этап 1 — реестр + загрузчик паспортов (вечер, ~100 строк Python).**
`tools/agents/registry.json` (инструменты: имя, контракт, права по ADR-004)
+ `tools/agents/run_agent.py`: читает паспорт из `Memory/Agents/*.md` как
system prompt, даёт 1–2 инструмента из реестра, вызывает шлюз :31415,
пишет отчёт в каноническом формате + лог рукопожатий. Бэрримор = диспетчер,
выбирающий следующий паспорт.

**Этап 2 — первый сквозной сценарий (неделя).** Холмс-аудит по расписанию →
отчёт → Соломон приоритизирует находки → задачи ложатся в лиджер
`Tasks/Active/`. Вот и «один парсит, другой анализирует, третий отчёты» —
только у вас это будут Холмс, Соломон и Бэрримор, с мандатами и журналом.

**Этап 3 — метрики, потом масштабирование.** Только после того как один
сценарий работает месяц: журнал рукопожатий (кто, кого, сколько токенов,
вердикт), доля задач, закрытых без правок человеком. И правило роста:
**новый агент = новый паспорт + 1 инструмент + 1 измеримая метрика.** Нет
метрики — нет агента. Двадцать агентов наберутся сами, когда двадцать задач
докажут пользу.

## 7. Фреймворки — когда всё-таки понадобятся (шпаргалка)

| Инструмент | Сильная сторона | Когда брать вам |
|---|---|---|
| LangGraph | Состояние, циклы, откат шагов | появятся длинные самокорректирующиеся цепочки |
| CrewAI | Ролевые команды (ближе всего к паспортам) | захотите готовый «экипаж» вместо своего диспетчера |
| AutoGen / MS Agent Framework | Диалоги агентов между собой | нужны споры/переговоры агентов |
| OpenAI Agents SDK | Лёгкий, минимум церемоний | быстрый прототип вне Python-экосистемы |
| PydanticAI | Типизированные контракты инструментов | если реестр инструментов перерастет в код |
| n8n (self-hosted) | Визуальные цепочки, триггеры, интеграции | наглядная замена cron-скриптам, DevOps-friendly |
| MCP-серверы | Стандартные «руки» (git, файлы, браузер) | как только агентам понадобится внешний мир |

Вывод: ваш stdlib-путь (ADR-003/004/005) сегодня вернее фреймворка.
Показательная цитата обзоров 2026: «каждый фреймворк решает оркестрацию —
ни один не решает память» (Shodh, апр. 2026). Память у вас уже своя:
файлы + git + паспорта. Фреймворк брать, когда реестр и диспетчер перестанут
влезать в ~200 строк — и то сначала MCP, потом фреймворк.
