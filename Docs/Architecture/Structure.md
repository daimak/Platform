# Архитектура платформы eVo

> Версия: 0.1  
> Обновлено: 12.07.2026

---

# Назначение

Данный документ определяет структуру проекта eVo и назначение каталогов верхнего уровня.

Главная задача документа — сохранить архитектурную целостность проекта по мере его развития и не потерять контекст принятых решений.

---

# Основной принцип

Платформа разделена на четыре независимые области:

- **Платформа** — программные компоненты, необходимые для работы eVo.
- **Память** — долговременные знания и контекст системы.
- **Рабочее пространство** — проекты и данные пользователя.
- **Документация** — описание решений, правил и архитектуры.

Эти области не должны смешиваться.

---

# Каталоги

## Core

Ядро платформы.

Содержит базовые механизмы работы системы, общие сервисы, инфраструктурные компоненты и фундаментальные абстракции.

Не содержит пользовательских данных и логики отдельных проектов.

---

## Modules

Функциональные модули платформы.

Каждая крупная возможность системы должна по возможности существовать как отдельный независимый модуль.

---

## Interface

Все способы взаимодействия пользователя с системой:

- терминальный интерфейс;
- веб-интерфейс;
- API;
- будущие графические интерфейсы.

---

## eVo

Интеллектуальная часть платформы.

Содержит:

- планирование;
- анализ;
- принятие решений;
- управление задачами;
- взаимодействие с памятью.

Это поведение системы, а не хранилище знаний.

---

## Memory

Долговременная память eVo.

Содержит:

- индексы;
- связи;
- метаданные;
- внутренние структуры хранения контекста.

Пользовательские файлы здесь не хранятся.

---

## Workspace

Рабочее пространство пользователя.

Содержит:

- проекты;
- документы;
- изображения;
- исходные материалы;
- артефакты.

Пример:

Workspace/
└── eVo/
├── Brand/
├── Documentation/
└── Assets/

---

## RFC

Архитектурные предложения и решения.

Значимые изменения платформы сначала описываются здесь.

Структура:

RFC/
├── Drafts/
├── Accepted/
├── Rejected/
└── Backlog/

---

## RFC/Backlog

Хранилище архитектурных идей, которые определены, но еще не реализованы.

Это не список задач.

Здесь сохраняются:

- будущие направления развития;
- потенциальные технологии;
- архитектурные вопросы;
- идеи, требующие возвращения в будущем.

---

## Notes

Рабочие заметки.

Черновики, мысли, исследования и временные записи.

Материалы отсюда могут позже перейти в RFC или документацию.

---

## Tools

Вспомогательные инструменты разработки.

Скрипты:

- обслуживания;
- миграции;
- диагностики;
- автоматизации.

Не являются частью основной платформы.

---

# Архитектурные правила

1. Core не зависит от Interface.
2. Modules используют Core.
3. eVo использует Core, Modules и Memory.
4. Workspace принадлежит пользователю.
5. Memory принадлежит системе.
6. Каждый каталог имеет одну понятную ответственность.
7. Каждое крупное решение должно иметь объяснение причины.

---

# Правила документации

- Вся внутренняя документация проекта ведется на русском языке.
- Названия каталогов, файлов кода, классов и API могут оставаться на английском языке.
- Документация должна объяснять не только "что сделано", но и "почему".

---

# Принцип развития

eVo должен сохранять не только результаты работы, но и контекст появления этих результатов.

Любой компонент проекта должен отвечать на вопрос:

**"Почему это существует?"**
