# ЛИДЖЕР — что за сила поселилась в проекте (объяснение для владельца)

*Памятка Дмитрию от ZCode, 01.11.2026. Разжёвано до мелочей, как просил Sovereign.*
*Факты сверен с реальными файлами: Memory/Engineering/Tasks/README.md, git-история, карточки.*

---

## 1. Что это — одним предложением

**Лиджер** (от английского *ledger* — «гроссбух», бухгалтерская книга) — это папка
`Memory/Engineering/Tasks/`, где **каждая задача — один JSON-файл-карточка**. Всё.
Никакой магии и базы данных: папка, в которой лежат файлы с задачами.

```
Memory/Engineering/Tasks/
├── README.md      ← правила лиджера (кто и как может его трогать)
├── Active/        ← живые задачи (сейчас 13 карточек + одна только что закрытая)
│   ├── kali-pentest-lab.json     ← твоя Kali-лаборатория
│   ├── rotate-langsmith-freellmapi.json  ← ротация ключей
│   └── ... (одна задача = один файл)
└── Archive/       ← кладбище: закрытые задачи уезжают сюда навсегда
```

## 2. Откуда он взялся (история, проверено по git)

**29.10.** Мы строили Бэрримора — дворецкого, который каждое утро собирает тебе бриф
(«что просрочено, что горит»). И выяснилось, что задачи тогда жили... надписями на
плашке дашборда, то есть **внутри кода app.js**. Поменял надпись — потерял задачу.
Чаты с ИИ, в которых обсуждались дела, тоже умирают каждый день (мы это пережили
дважды — хендшейки ENTRY-POINT). Тогда задачи вынесли из кода и из чатов в файлы:
так родился «Barrymore Task Ledger» — сначала 5 карточек, которые раньше были
надписями на плашке.

**30.10.** Холмс (аудитор) научился превращать свои находки в карточки лиджера
автоматически: нашёл проблему → создал карточку `holmes-*.json` → задача не
потеряется. Реестр инструментов (registry.json v3) получил право `ledger.write`.

**С тех пор** лиджер — единственное место в проекте, где «живут» задачи. Чаты
приходят и уходят, карточки остаются.

## 3. Для чего он нужен — три реальные функции

1. **Память, которая переживает смерть чатов.** Каждый новый чат ZCode читает
   точку входа → журнал → лиджер и сразу знает все дела, даже если предыдущий
   чат умер и ничего не успел передать.
2. **Папка с бумагами Бэрримора.** Утренний бриф и сводка прогона собираются
   из этой папки: Бэрримор не «помнит» задачи — он их читает отсюда.
3. **Стык между агентами и тобой.** Холмс нашёл уязвимость — создал карточку —
   на дашборде появилась задача с галочкой — ты одобрил — задача поехала в работу.
   Без карточки Холмс мог бы «написать в отчёте», и ты бы это никогда не прочитал.

Главное правило, которое из этого следует: **«Нет карточки в лиджере — задачи не
существует»**. Это тот же принцип, что у штата поместья: «нет строки в штате —
сотрудника нет». Сказанное в чате — это разговор. Записанное в лиджер — это задача.

## 4. Чем владеет: из чего состоит карточка

Разберу на примере твоей карточки `kali-pentest-lab.json` (ты её уже видел):

| Поле | Что значит | Пример |
|---|---|---|
| `id` | Имя файла и постоянный номер задачи. Никогда не переиспользуется, даже после архива | `kali-pentest-lab` |
| `title` | Название по-человечески | «Kali Linux лаборатория: VMware + белый пентест» |
| `source` | Кто заказал: `user` (ты) или агент | `user` |
| `priority` | `urgent` (горит — Kali, ротация ключей) или `regular` | `urgent` |
| `status` | Только `active` или `done`, других нет | `active` |
| `description` | Что за задача и откуда слово владельца | цитата Дмитрия от 30.10 |
| `steps` | Шаги-рецепт, у каждого свой `dod` (**Definition of Done** — «как поймём, что шаг сделан») | шаг 7 «спец-учётка» |
| `constraints` | Красные линии: что нельзя делать при исполнении | «БЕЛЫЙ пентест — только свои системы» |
| `links` | Ссылки на план, документы, смежные задачи | KALI-PENTEST-PLAN |
| `history` | **Дневник карточки**: кто, когда и что в ней менял. Записи не стираются — как в бухгалтерской книге | см. 3 записи внутри |

`history` — сердце лиджера: даже если задача переезжает из чата в чат и её трогают
разные ИИ, по дневнику видно, кто и почему изменил статус, а не «кто-то что-то там».

## 5. Жизненный цикл задачи (короткий и строгий)

```
Слово Дмитрия (или находка Холмса)
        ↓
карточка создана в Active/ (status: active)
        ↓
работа по шагам, каждый шаг = запись в history
        ↓
ты жмёшь «Mark Done» в дашборде  ← ЕДИНСТВЕННЫЙ способ закрыть задачу
        ↓ (48 часов карточка ещё видна в Active/ и в брифе)
авто-переезд в Archive/YYYY/MM/ (навсегда, с timestamp'ом)
```

Два строгих правила:
- **Закрыть задачу можно только кнопкой «Mark Done» в дашборде.** Даже ИИ не может
  объявить задачу сделанной по собственной воле — это твоя кнопка.
- **Archive — не мусорка.** Оттуда ничего не удаляется; ID из архива не
  переиспользуются, чтобы старая и новая задача с одинаковым именем не перепутались.

## 6. Чем лиджер НЕ является (чтобы не путаться)

- **Не план этапов.** Крупный план аудита живёт в `Memory/Engineering/PLAN.md`.
  Лиджер — конкретные задачи с владельцем и статусом.
- **Не журнал сделанного.** Что фактически сделано — `Memory/Engineering/LOG.md`
  (записи E-NNN, append-only). Лиджер — что *предстоит и кем принято*, журнал — что *сделано*.
- **Не расписание.** Никаких cron'ов и таймеров. Задача не «сработает» сама —
  её выполняет живая сессия или агент по твоему слову.
- **Не единственная истина.** По правилам Memory/Engineering: при расхождении
  записи и реальных файлов/git — верить файлам и git, а расхождение фиксировать.

## 7. Что ты можешь делать руками (шпаргалка)

- **Посмотреть все задачи:** открыть `Memory/Engineering/Tasks/Active/` — или просто
  спросить меня «покажи лиджер».
- **Закрыть задачу:** дашборд → карточка → «Mark Done».
- **Поставить задачу:** сказать мне (или любому чату) — карточку создаст он.
  Вручную: скопировать любую карточку, поменять `id`/`title`, положить в Active/.
- **Изменить приоритет/условия:** сказать мне — я отредактирую и отмечу в history.
- **Отменить/похоронить:** статус менять руками не надо — скажи мне, задача уедет
  в архив с честной записью в history.

## 8. Как быстро проверить меня (протокол «доверяй, но верифицируй»)

```bash
ls Memory/Engineering/Tasks/Active/        # сколько задач, какие
cat Memory/Engineering/Tasks/README.md     # правила лиджера (оригинал, по-английски)
git log --oneline -5 -- Memory/Engineering/Tasks/   # кто и когда трогал карточки
```

---

*Итого одной фразой: лиджер — это канбан-доска из JSON-файлов: карточка = задача,
Active = «в работе», кнопка Mark Done = «сделано», Archive = «навсегда». Он появился,
потому что чаты умирают, а дела должны выживать.*
