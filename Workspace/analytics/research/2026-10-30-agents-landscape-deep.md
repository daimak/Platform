# Агентные фреймворки и паттерны 2026 для персональной LLM-платформы

*Дата: 2026-10-30. Контекст: Platform Evo — однопользовательская платформа (markdown + Python stdlib + статический HTML), локальный OpenAI-совместимый шлюз на localhost:31415, один полу-агент по доктрине «агент = паспорт + инструмент + метрика», диспетчер ~200 строк. Метод: веб-поиски (14 запросов) + чтение первоисточников.*

---

## Сводка

- **Консенсус 2026 — простые паттерны поверх сырого API.** Anthropic в «Building Effective Agents» прямо фиксирует: самые успешные внедрения «не использовали сложные фреймворки», а строились из композируемых паттернов в нескольких строках кода; фреймворк прячет промпты и ответы — главный отладочный актив персональной платформы. Наш 200-строчный диспетчер не «пока влезает», а находится точно в мейнстриме.
- **MCP стал стандартом, но стандартом с ценой.** ~500 млн загрузок SDK в месяц, 47 267 серверов в официальном реестре, передача в Linux Foundation (дек 2025). Обратная сторона: 382 CVE (из них 79 Critical), tool poisoning в 5,5% изученных серверов, 9,57% серверов без аутентификации, 40,6% мультиверсионных серверов молча меняют описание. Для собственных инструментов одного пользователя MCP — лишний слой; он нужен при интероперабельности с внешними клиентами/серверами.
- **Самая переносимая идея года — Agent Skills (SKILL.md).** Открытый формат: папка с markdown + YAML-frontmatter, прогрессивная загрузка (~100 токенов метаданных в контексте, тело — по триггеру). Это буквально «паспорт в markdown» без SDK — идеальная точка эволюции нашей доктрины.
- **Провалы пилотов — не про модель, а про обвязку и скоуп.** MIT NANDA: ~95% корпоративных GenAI-пилотов не дают P&L-эффекта; 88% агентных проектов не доходят до прода — расползание скоупа (34%), качество данных (27%), безопасность (14%). В рантайме: компаундинг ошибок в цикле, хрупкие коннекторы, «невидимая» инфраструктура.
- **Рекомендация для Platform Evo:** не внедрять ни MCP, ни фреймворки сейчас. Первый шаг — (1) перевести паспорта на совместимый с Agent Skills формат с прогрессивной загрузкой, (2) вынести гардрейлы (права, подтверждения side-effect инструментов) в детерминированный код диспетчера, (3) добавить JSONL-трассировку с учётом токенов. MCP-адаптер в шлюзе — отложить до конкретного стороннего сценария.

## Ландшафт 2026

### 1. MCP (Model Context Protocol)

**Что даёт.** Открытый стандарт подключения AI-приложений к данным и инструментам («USB-C для AI»). Экосистемные цифры на конец 2026: 231,9 млн загрузок TypeScript SDK в npm за сентябрь 2026 (год назад — 31,3 млн), 260,8 млн в PyPI за 30 дней; суммарно ~500 млн/мес по Tier-1 SDK; в официальном реестре 47 267 активных серверов (11 869 добавлено в один сентябрь 2026). В декабре 2025 проект передан под эгиду Linux Foundation (Agentic AI Foundation, 286 организаций). MCP поддержан всеми крупными вендорами (OpenAI, Google, Microsoft добавили поддержку в 2025) и клиентами: Claude, ChatGPT, VS Code, Cursor.

**Что требует.** Запуск серверных процессов (stdio или Streamable HTTP), JSON-RPC-транспорт, реализацию клиентской стороны (список инструментов, конвертация в tool-calls, lifecycle), конфигурацию и — для удалённых серверов — аутентификацию. Важно: спецификация **2026-07-28 переведена на stateless-модель** и **депрекировала Roots, Sampling, Logging и Dynamic Client Registration** — т.е. стандарт активно меняется, и совместимостью придётся заниматься самому.

**Цена безопасности.** 382 MCP-связанных CVE в NVD (324 опубликованы в 2026; 79 Critical, 161 High). Класс атак — tool poisoning: вредоносные инструкции в описаниях инструментов, невидимые человеку, но видимые модели (Invariant Labs, апр 2025); Microsoft выпустил руководство по защите от indirect prompt injection в MCP. Исследование 45 живых серверов (1312 тестов) показало: атака проходила не через отравленный, а через **уже одобренный пользователем** инструмент — то есть ручное одобрение при подключении не спасает. Плюс supply-chain-дрейф: 40,6% мультиверсионных серверов меняли рекламируемые описания без уведомления.

**Вывод для одиночки.** MCP оправдан, когда нужно подключать *чужие* инструменты к *разным* клиентам или нужен стандартизованный барьер для приватных данных. Если инструменты свои и клиентов свой — прямые tool-calls проще, быстрее в отладке и покрывают ~90% случаев (позиция, устойчиво повторяющаяся в обзорах 2026).

### 2. Claude Code / Agent Skills

Skills — «аккуратно подписанные папки экспертизы»: папка с SKILL.md (YAML: name, description) + опциональные скрипты и справочники. Механика — **прогрессивная загрузка в три уровня**: в контексте постоянно только имя+описание (~100 токенов на скилл), тело SKILL.md подгружается при совпадении с задачей, связанные файлы — по мере надобности. Официальные рекомендации: тело скилла < 500 строк. С 2026 это **открытый стандарт Agent Skills**, не привязанный к Anthropic: работают в Claude Code, API и Agent SDK. Claude Agent SDK — «harness»: цикл агента + sandbox + права; в апреле 2026 SDK разделили на sandbox и harness.

Ключевое: формат скиллов — это просто **markdown-файлы с фронтматтером**, читаемые любым кодом. Никакой SDK не нужен, чтобы adoptить сам паттерн.

### 3. OpenAI Agents SDK

Выпущен в марте 2025 как production-наследник экспериментального Swarm: «лёгкий пакет с малым числом абстракций». Примитивы: agents, handoffs, guardrails, sessions; в октябре 2025 добавлен AgentKit (evals, RFT), в апреле 2026 — разделение sandbox/harness. Позиционируется как один из самых лёгких полноценных SDK 2026. Нюансы для нашего контекста: SDK заточен под модели и API OpenAI (Responses API); наш шлюз OpenAI-совместим, но не идентичен — потребуется адаптация; и это всё равно зависимость, прячущая промпты и цикл.

### 4. CrewAI / LangGraph / AutoGen — эволюция за год

- **LangGraph** — лидер «производственного контроля»: явные графы узлов/рёбер, общее состояние, дооб wired вручную. Выбор, когда нужна точная детерминация переходов.
- **CrewAI** — ролевые «команды» (crew): быстрые прототипы и MVP, но меньше контроля на сложных stateful-сценариях; за год добавил Flows.
- **AutoGen** — поглощён **Microsoft Agent Framework** (слияние с Semantic Kernel, линия Magentic-One), силён в Azure/Microsoft-экосистеме.
- Общий фон 2026: консолидация, «меньше хайпа, больше автономии». Критика повторяется: границы ролей «текут», координационная нагрузка растёт быстрее ожиданий; фреймворки «сильны в ясности, а не в эмерджентности». Пост-мортем Vercel (дек 2025): **больше агентов и инструментов — хуже результаты**. Безопасность фреймворков тоже не безупречна: CVE-2026-2256 (MS-Agent) и CVE-2026-25253 (OpenClaw) давали эскалацию доступа.

Все три решают задачу мульти-агентной оркестрации в масштабе, которой у одиночки с одним агентом нет.

### 5. Lightweight-варианты (роль-файлы + скриптовый цикл)

Формула Уилсона стала общим знаменателем: *«An LLM agent runs tools in a loop to achieve a goal»*. Направление «no framework» укрепилось: minimal-agent (~100 строк ReAct), «You Probably Don't Need an Agent Framework», множественные туториалы «цикл изнутри без LangChain». Паттерн Aug 2026 — «deterministic control»: промпты не выживают в длинных циклах, надёжность даёт скучная детерминированная инфраструктура вокруг цикла (права, ретраи, лимиты шагов, журнал). Anthropic в «Building Effective Agents» даёт ту же лестницу: augmented LLM → prompt chaining → routing → parallelization → orchestrator-workers → evaluator-optimizer → agent-цикл, и советует начинать с простейшего, добавляя сложность только при доказанной пользе.

## Провалы и причины

**Масштаб.** MIT NANDA (Media Lab), «The GenAI Divide: State of AI in Business 2025»: **~95% корпоративных GenAI-пилотов не дают измеримого P&L-эффекта** при затратах $30–40 млрд. Forbes о причинах: компании «избегают трения» — не встраивают AI в рабочие процессы; инструменты не сохраняют фидбек и не учатся. Отчёт критиковали за методологию (малая выборка, размытое определение «провала»), но направление критики совпадает с другими источниками.

**До прода не доходят.** Фреймворк DigitalApplied (март 2026): **88% агентных проектов не достигают production** (коррелирует с Gartner 2025 — 85%, и McKinsey — <20% пилотов масштабируются за 18 месяцев). Разбивка причин: расползание скоупа — 34%, качество данных — 27% (вместе 61%), блокеры безопасности — 14% (в основном отсутствующие регламенты/контроли, а не реальные уязвимости), интеграционная сложность — 9%, перерасход средств — 7% (недооценка стоимости инференса: 3–8 LLM-вызовов на многошаговую задачу), провалы governance — 5%, сопротивление организации — 4%. Средняя стоимость провалившегося проекта — $340 тыс. Рекомендации авторов: v1.0 = один воркфлоу с явными исключениями из скоупа; аудит данных до кода; безопасность параллельно с разработкой; модель стоимости на 1x/5x/10x объёма; именованный владелец и инцидент-ранбуки до выката.

**В рантайме.** Инженерные разборы 2026 сходятся на трёх механизмах: (1) **плохой retrieval-контекст** — агент получает не те данные и уверенно идёт не туда; (2) **хрупкие коннекторы инструментов** — API ломаются на реальных данных; (3) **компаундинг ошибок** — вероятность провала растёт мультипликативно по шагам цикла. Общий тезис: «большинство агентов падает не из-за модели, а из-за невидимой инфраструктуры вокруг неё». Отсюда центральный тренд — context engineering и трассируемость.

**Специфически агентная причина провалов безопасности:** одобрение инструментов человеком — недостаточная защита (атака через уже одобренный инструмент, см. выше); выводы инструментов нужно считать недоверенным вводом.

## Критерии выбора для одного человека с локальным шлюзом

1. **Цена поддержки.** Каждая зависимость — чей-то релизный цикл, который ты тянешь один: смена спеки MCP (депрекации 2026-07-28), CVE фреймворков, breaking changes SDK. Для stdlib-платформы любая внешняя зависимость должна покупать себе место явно. Правило: внедрять только то, что переживёт твоё отсутствие внимания 3 месяца.
2. **Наблюдаемость.** Абстракция, прячущая промпты и ответы — главный враг отладки (прямое предупреждение Anthropic: неверные предположения о внутренностях — частый источник ошибок у их клиентов). Токены — прокси и для денег, и для латентности, и для контекстного окна: по данным Keito, прямой учёт токенов покрывает лишь 30–40% реального расхода (циклы, ретраи, рост контекста). Для локального шлюза деньги не релевантны — релевантны окно контекста, латентность и качество; достаточно JSONL-журнала шагов + счётчиков. Langfuse (self-hosted) / OTel GenAI — следующий уровень, когда простого журнала не хватит.
3. **Безопасность / ограничение прав.** Для одиночки модель угроз — в основном случайно подключённый сторонний код и indirect prompt injection через данные. Митигации: read-only по умолчанию (уже сделано), явные allow-lists инструментов на уровне паспорта, подтверждение/логирование side-effect операций, проверка прав в детерминированном коде диспетчера (не в промпте), трактовка выводов инструментов как недоверенного текста, никаких непроверенных сторонних MCP-серверов.
4. **Стоимость токенов.** Локальный шлюз = $0 за инференс, но контекстное окно — дефицитный ресурс: описания инструментов и системные промпты съедают его до начала работы. Отсюда ценность прогрессивной загрузки (скиллы: ~100 токенов метаданных вместо полного тела) и минимализма в списке инструментов (Vercel: больше инструментов — хуже результаты).
5. **Скорость отладки в 2 часа ночи.** 200-строчный файл, который читается целиком, побеждает фреймворк, требующий изучения документации, чтобы понять, почему цикл завис. (Практический критерий: если починка требует чтения чужого исходника — это долг.)

## Рекомендация для Platform Evo

### Первый шаг (дни-недели, без новых зависимостей)

1. **Паспорта → формат Agent Skills.** Переоформить паспорта как SKILL.md-совместимые файлы (frontmatter: name, description; тело — инструкция). Диспетчер держит в контексте только name+description (~100 токенов), а тело загружает инструментом read-only по триггеру/запросу модели. Это даёт прогрессивную загрузку, совместимость с открытым стандартом (файлы можно будет переиспользовать в Claude Code и др.) и не меняет доктрину — это её формализация.
2. **Гардрейлы в диспетчере.** Всё, что сейчас есть в правах паспорта, проверять кодом до вызова инструмента; для side-effect инструментов — требование подтверждения и обязательное логирование; выводы инструментов передавать модели как недоверенный текст с маркером источника. Это ответ на главный рантайм-провал (компаундинг ошибок + инъекции через данные).
3. **JSONL-трассировка + счётчики токенов в метрике.** Одна строка JSON на шаг: время, вызов инструмента, входные/выходные токены, латентность, статус. Это минимальная наблюдаемость из критериев и готовая база для будущих evals.

### Что отложить и почему

- **MCP-клиент в шлюзе.** Отложить до появления конкретного стороннего MCP-сервера, нужного регулярно (например, файловая система/поиск, которые неудобно писать самому). Когда придёт время — реализовывать как **адаптер «MCP → OpenAI tools» на стороне шлюза** (диспетчер по-прежнему видит обычные tool-calls), только stdio-транспорт, только известные локально серверы. Обоснование отсрочки: для своих инструментов MCP — двойная работа; спека нестабильна (депрекации 2026); безопасность экосистемы хуже средней (382 CVE, 9,57% без auth, 40,6% молчаливого дрейфа описаний).
- **Langfuse / OpenTelemetry GenAI.** Отложить до момента, когда JSONL-журнал перестанет отвечать на вопросы (поиск по трассам, сравнение запусков, регрессии качества). Самодостаточный self-host вариант известен.
- **Фреймворки (LangGraph, CrewAI, AutoGen/MS Agent Framework, OpenAI Agents SDK).** Не «отложить», а «не брать» без события-триггера. Триггером может быть только устойчивая multi-agent задача с состоянием — чего у одного пользователя с одним агентом не предвидится.

### Чего не делать

- **Не подключать сторонние MCP-серверы пачкой «поиграть»**: tool poisoning в 5,5% серверов и дрейф описаний превращают это в лотерею; сторонний код — главный вектор одиночки.
- **Не строить мульти-агентную оркестрацию «про запас»**: пост-мортем Vercel (больше агентов/инструментов — хуже) и компаундинг ошибок делают это антипаттерном для персонального масштаба.
- **Не расширять скоуп одного агента на несколько воркфлоу за раз**: 34% провалов — это ровно это. Один агент = один воркфлоу, новый сценарий — новый паспорт.
- **Не переносить права из кода в промпты**: «читай только read-only» в тексте промпта — не право, а пожелание; право проверяет диспетчер.

### Итог по доктрине

Доктрина «агент = паспорт + инструмент + метрика» консистентна с консенсусом 2026: паспорт ≈ skill + права (Agent Skills / guardrails), инструмент ≈ tool registry (свой, без MCP-обвязки), метрика ≈ trace + token accounting (наблюдаемость). Менять парадигму не нужно — нужно формализовать формат паспорта (SKILL.md), закрепить гардрейлы в коде и добавить трассировку. Всё это вместе — примерно та же пара сотен строк, что и текущий диспетчер.
