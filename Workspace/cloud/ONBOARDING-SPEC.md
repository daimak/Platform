# ТЗ лейна О «ОБЛАКО»: скрипты освоения удалённых машин (DigitalOcean + Yandex Cloud)

**Заказ Sovereign (06.11 ~23:40):** «отдельным лейном запусти создание скриптов по освоению удалённых машин, куда мы имеем доступ — чтобы не терять времени, когда зарегаемся на площадках». Регистрация будет руками Дмитрия (карты/телефоны — только его руки); лейн готовит ВСЁ, что выполняется на серверах после регистрации.

## Железные правила лейна (как у всех + свои)

1. Корень `C:\Work\Platform`. **Git запрещён.** Сервер 8765 не трогать. Суб-агентов не спавнить.
2. Маячок: `Workspace/analytics/research/money-uz-3days/_cloud-progress.md` — строка «HH:MM — шаг — результат» после каждого шага.
3. Писать ТОЛЬКО в `Workspace/cloud/` (кроме маячка). Ничего не удалять.
4. **Секретов в скриптах НЕТ**: ключи/токены — только через переменные окружения и упоминания «возьмётся из Workspace/.env руками». Никаких карт, паролей, токенов — даже примеров.
5. Скрипты — bash, target Ubuntu 24.04 LTS на обеих площадках; dry-run-безопасность: скрипт без аргументов печатает help, не выполняет разрушительное; идемпотентность (повторный запуск не ломает).
6. Web-проверки фактов (актуальные имена инстансов DO, yc команды) — последовательно; если не уверен в имени SKU — написать TODO-метку вместо выдумки.

## Deliverables (все в `Workspace/cloud/`)

1. `bootstrap.sh` — универсальная инициализация свежей ВМ (аргумент `do|yc`): apt update/upgrade, timezone Asia/Tashkent, ufw (22,80,443 + порты стенда), fail2ban, SSH hardening (key-only, no root password, PermitRootLogin prohibit-password), создание пользователя deploy с sudo, unattended-upgrades, docker + docker compose plugin. Идемпотентно.
2. `cloud-init-do.yaml`, `cloud-init-yc.yaml` — то же самое как cloud-init user-data (ВМ рождается уже настроенной); параметризовано ключом SSH (плейсхолдер `{{SSH_PUBLIC_KEY}}` — вставляет Дмитрий, не агент).
3. `install-k3s.sh` — одномерный k3s-кластер (master; флаг `--agent <url>` для второй машины): практика k8s на обоих облаках.
4. `deploy-polygons.sh` — деплой стендов в docker compose: Juice Shop (секьюрити-цель, СВОЯ), DVWA, n8n, Uptime-Kuma (мониторинг), WireGuard (туннель к домашней лабе). Каждый сервис — отдельный compose-файл в `Workspace/cloud/compose/`, порты и пароли генерации — только плейсхолдеры/openssl-генерация на месте.
5. `probe-machine.sh` — **«освоение удалённой машины»**: снимок добычи с любой свежей ВМ (ОС, ядро, CPU/RAM/диск, внешние/внутренние IP, открытые порты ss, гео IP (curl к бесплатному geo-сервису), docker/k3s версии, пинг/трейс до узла-ориентира) → markdown-отчёт `probe-<host>.md`. Это скрипт «куда мы имеем доступ и что умеет машина».
6. `README-УТРО.md` — чек-лист Дмитрия на утро регистрации (10 шагов по порядку для DO и для YC: что кликать руками, где взять API-токен, куда его положить (`Workspace/.env`, НЕ в git), команда первой загрузки скриптов на машину (scp/yc scp/doctl), запуск bootstrap, проверка probe). Плюс таблица «что куда деплоим» (см. план использования).
7. `token-meter` не нужен; событие в журнал: append_event('cloud.lane','О',{'step':'...'}) после каждого deliverable.

## Критерий готовности

README-УТРО читает человек, не знавший контекста, и выполняет за ~30 минут на обеих площадках без гаданий. Скрипты синтаксически валидны (`bash -n`). В финале маячка — строка «ГОТОВО: N файлов, bash -n чист».
